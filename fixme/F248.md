# F248. **[resolved]** moving a document's row by retract and assert drops the prose above it — a file's header goes with its first record

**2026-10-03**, found in `git status` after Henri's two minutes with
`examples/gui/drag.ges`: `drag.dots` came back as three bare lines, its
three-line header gone.  The reader attaches the prose above a record to
that record (`records`' `above`), and the file's opening comment is
above the first one; `place`'s `put` is `retracting` then `asserting`,
so dragging dot `a` retracted its line *with* the header and asserted a
new line with none.

    git show 5aec526:examples/gui/drag.dots | head -4     # the header
    # drag dot a anywhere and let go; the file then starts at `dot  name`

The tests did not see it because their document has no comments
(`test_reactors.py`'s `DOTS`).

**Not fixed the same day**; two ways out were written down — `retracted`
keeping the removed record's `above` for the record asserted in the same
step, or a move of a non-key field going through `documents.moved`.

**Resolved 2026-10-03, the second way.**  `MoveTo`'s second row may be
the whole new row as well as the new key (`facts.fact_of` already took
either), and `documents.moved` rewrites every field it names in place —
`notes.retune` for `.notes`' own kinds, `documents._rewritten` for a
kind a program declares; the `.notes`-only refusals run only where
those kinds exist.  `drag.ges` and its control `drag-today.ges` put one
`MoveTo` instead of a retract and an assert.  Held by `test_reactors.py`'s
`test_a_drag_changes_one_number_and_keeps_the_files_prose`, whose
document has a header and a comment beside a dot — red on both programs
with their old `put` restored.

**A retract and an assert still drop a record's prose**, and that is
the design rather than the defect: F200 decided that the lines above a
record belong to it, so a retraction takes them.  The defect was a
*move* written as the pair.
