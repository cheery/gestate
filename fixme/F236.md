# F236. **[resolved]** the state chunk carried the knobs, the routing and the seed, and not the `from score` switches, so every reopened session handed the banks back to the piece

**Henri, 2026-09-16:** *"'from score' parameters end up turning back
'on' when I restart reaper DAW after they have been turned 'off'."*

Exactly right, and the cause is an omission rather than a behaviour.
`state_save` in `shell/clap/src/lib.rs` wrote the magic, the version,
the shape hash, every **knob** control, the routing rows and the seed.
`plays_score` was in none of it, and `state_load` therefore never set
it — so a fresh instance came up on `default_plays()`, which for a piece
that writes every bank is *on* for every bank.

**What makes it a gap rather than a decision** is the neighbour.  The
routing matrix is the other half of the same panel — sixteen channels
*into* a bank against one question about who plays it, and the plugin's
own `params_get_info` puts them in one module called `score`.  One half
was saved and the other was not.

**And the switch is the whole point of the panel.**  A piece that writes
every bank accepts MIDI on the diagonal *and* is scored, so the switch is
how a player takes a bank away from the piece and plays it by hand.  A
setting that forgets itself between sessions is worse than one never
offered: the player sets it, hears it work, and finds it undone tomorrow
with nothing to blame.

## Measured before it was fixed

`test/test_export.py` is already a miniature CLAP host in ctypes with a
state round-trip helper, so this was driven rather than read: find every
`… from score` parameter, turn one off through `params.flush` — the path
the plugin documents for a knob moved with the transport stopped —
confirm it reads back off, save, load into a second instance of the same
`.clap`, and ask it again.  It came back **1.0**, and the assertion says
so in the message.  Green after the fix.

*One harness fault on the way, worth the line:* the first version sent
the parameter in a `process` block with null audio buffers, which the
plugin refuses before it reaches the events, and the test failed at
*"the switch did not turn off at all"*.  That was the test being wrong,
not the plugin, and the wrong assertion is the one that said so.

## Resolved — 2026-09-16

The switches are appended to the state chunk after the seed, and read
back as optional, which is **the same move the seed itself documents
one line above**: a field on the end is one an older state simply does
not have, and bumping `STATE_VERSION` would make every session saved
before today fail to load, for the sake of a number nobody reads.

A count that disagrees is skipped rather than refused — a shape change
is `shape_hash`'s job, and failing a whole session over one panel would
lose the knobs and the routing with it.

gate: `test/test_export.py::test_a_switch_turned_off_is_still_off_after_the_host_reopens`
— red on the unfixed shell at the right assertion, green after, and the
other fourteen tests in that file still pass, which is what says the
appended field did not disturb the older ones.
