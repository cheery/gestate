# F250. **[resolved]** a canvas opened before it had built could stay a lane with no notes: the window ticked it while its rows were being written

**2026-10-03**, found driving resize in the real window
(`card:gui-is-difficult.md` §"Built — resize, as named holds").  Open
`carry.ges`, press Ctrl-Tab at once, and the canvas drew its lane and no
notes, for good: rewriting `tune.notes` brought nothing back.  The same
picture had been seen once under the suite's load and not reproduced
(§"Built — the notes editor's note hand", the driven run).

`workbench._begin` runs `Workbench.start` on its own thread, and the
window's loop ticks whatever `bench.substrate` is.  `_load_substrate`
published the new canvas first and fed its document after, so a frame
could tick the graph while `write_all` was writing it.  Headless, with a
thread building and the main thread running frames:

    ReactiveError: tail of a signal on the earlier heap: it has not been
    updated yet this step.

It ended with the lane alone.  In the window: 0 of 3 early opens drew
notes with the resize slice's desugaring, and 1 of 3 failed on the code
before it.  So the race is older than the slice, which made it more
frequent.

**Resolved the same day:** the rows are fed into the canvas before it is
published (`_feed_documents(fresh)`, then `self.substrate = fresh`).
Held by `test_reactors.py`'s
`test_a_canvas_is_published_only_once_its_rows_are_written`, red on the
code before.  Driven after it: 3 of 3 early opens drew all six notes.

**What it costs:** until the canvas is published the window has nothing
to draw, and its loop spins hot on that nothing, which slows the cold
build that shares the interpreter with it: 8.8 s headless against
3–6 s alone, and the full picture at about 12 s in the window.  The
code before drew the lane sooner and could lose the notes.  Not chased.
