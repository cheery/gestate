# What is "the tree"?

"The tree" is the name given in this project's documentation to the overall body of written material — journals, specifications, memory files, and rules — that governs and conditions how work is done on the gestate project. It is not a data structure in the code sense; it is a metaphor for the accumulated, structured documentation itself.

## Core definitions

Three descriptions of "the tree" appear directly:

- It is "a living system of documented methods, rules, and journal entries designed to teach its keeper and visitors through written practice" (`journal/2026-08.md`).
- It is "an append-only system that conditions the next session's behavior through deterministic rules, gates, and a consent register, functioning as a workplace for workers who do not remember" (`doc/notes/notes-on-the-find.md`).
- It is "an external, cached slow thinking system that stores the residue of past deliberation and conditions future fast passes" (`doc/notes/notes-on-cues.md`).

Together these descriptions frame the tree as a persistent, external memory: because each working "session" (an AI agent instance) does not carry memory forward on its own, the tree exists to hold decisions, rules, and lessons so that future sessions — who "do not remember" — can be conditioned by past deliberation rather than repeating it.

## Its parts and mechanisms

The tree is made up of the project's actual documents: `journal.md` (tracking unbuilt increments and design decisions), `fixme.md` (tracking divergences between implementation and spec), `roadmap.md`, `manifesto.md`, `vision.md`, the `spec/` directory, the `board/` card-tracking system, and the `doc/memory/` directory of distilled memory files — all cited across many entries in the context as interlocking pieces of this same documentary structure (`README.md`, `fixme.md`, `journal/2026-08.md`).

The tree operates through "deterministic rules, gates, and a consent register" (`doc/notes/notes-on-the-find.md`) — for example gate scripts like `tools/pre-commit.sh` and `tools/suite.py`, hooks in `.claude/settings.json`, and consent tracking in `doc/consent.md`. These mechanisms enforce behavior outside of any model's own judgment, consistent with the `weights-context-suite` memory's framing that rules must live in context and suite checks, never baked into "weights" (`doc/memory/README.md`).

## Its "jobs" and how they scale

One memory document, `smaller-models-and-the-tree`, analyzes the tree as having three distinct jobs — "structural rules, judgment norms, and initiative" — and studies how these degrade separately when smaller (9B, 1B) models are used instead of larger ones, with structural rules surviving best, judgment norms failing first, and initiative-taking the most fragile (`doc/memory/smaller-models-and-the-tree.md`, `doc/memory/README.md`).

## Summary

In short, within this repository's own self-description, "the tree" is the whole living, append-only documentary and rule system — journal, specs, board, and memory files together — that teaches and constrains both the human keeper and the AI sessions ("visitors") who work on the project, serving as an external memory and conditioning mechanism because the sessions themselves do not persist (`journal/2026-08.md`, `doc/notes/notes-on-the-find.md`, `doc/notes/notes-on-cues.md`).
